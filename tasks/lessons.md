# Lessons

- Before proposing changes to level spawning, inspect existing scene components and ask whether the level already has an authored spawn-point workflow. Preserve that workflow unless the user explicitly requests a replacement.
- When a user asks for a cleaner Unity interaction implementation, prefer a simple, component-driven approach over ad-hoc raycast/overlap logic and keep behavior explicit and maintainable.
- Never call `GameObject.FindWithTag` or `GameObject.FindGameObjectsWithTag` with custom tags without verifying or defining the tag in Unity's `TagManager` first, as Unity throws a fatal `UnityException` if a tag is queried that does not exist in the project settings. Prefer component-based registration or explicit serialized references.
- When creating UI procedurally or supporting authored scene references, always guard against re-instantiating elements if references are already assigned. Ensure background panels, decorative cards, and text labels inside buttons have `raycastTarget = false` to prevent invisible or overlapping graphics from blocking clicks to selectable controls.
- For imported environment lighting, never approximate fixture locations from mesh density or bounds. Identify the authored fixture geometry first, then snap each light directly beneath its matching fixture and verify the alignment in the Scene view.
- When a user asks to build UI in a Unity scene, author the Canvas and controls into that scene unless they explicitly request runtime-generated UI. Never present a Play Mode-only UI as a persistent scene edit; verify the hierarchy after exiting Play Mode.
